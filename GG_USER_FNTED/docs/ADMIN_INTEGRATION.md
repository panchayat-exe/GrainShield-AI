# GrainShield AI — Admin Integration Guide> This document is the complete reference for building the future **GrainShield AI Admin Dashboard**. The admin website shares the same Supabase project, PostgreSQL database, Auth system, Storage bucket, schema, and RLS rules as the user website. No data migration or separate database is needed.---## 1. Securely Granting Admin Role**Never** allow users to self-assign admin roles. The only trusted path is:### Option A: Direct SQL (via Supabase Dashboard → SQL Editor)```sql-- Run as a service-role operation or in the Dashboardselect public.set_user_role(  'user-uuid-here'::uuid,  'admin'::user_role);```### Option B: Service-Role API call (from a secure admin server)```typescriptimport { createClient } from "@supabase/supabase-js";const adminClient = createClient(  process.env.SUPABASE_URL,  process.env.SUPABASE_SERVICE_ROLE_KEY, // Never expose this to the browser);await adminClient.rpc("set_user_role", {  target_user_id: "user-uuid",  new_role: "admin",});```> [!CAUTION]> `SUPABASE_SERVICE_ROLE_KEY` must only ever exist on a trusted server, never in a browser bundle, environment variable prefixed with `VITE_`, or source control.---## 5. Admin Website Supabase Client Setup```typescript// admin-website/src/lib/supabase/client.tsimport { createBrowserClient } from "@supabase/ssr";// Same project URL and publishable key — NOT the service role keyexport const supabase = createBrowserClient(  process.env.NEXT_PUBLIC_SUPABASE_URL, // or VITE_SUPABASE_URL  process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY,);```The admin website uses the same publishable key. The database's RLS policies grant extra read access based on the user's `role` field in the `profiles` table.---## 6. Admin Authentication and Route Protection```typescript// admin-website: check role before rendering admin routesasync function requireAdmin() {  const {    data: { user },  } = await supabase.auth.getUser();  if (!user) redirect("/login");  const { data: profile } = await supabase    .from("profiles")    .select("role")    .eq("id", user.id)    .single();  if (!["admin", "super_admin"].includes(profile?.role ?? "")) {    redirect("/unauthorized");  }}```---## 7. How RLS Grants Admin AccessThe key database helper is `public.is_admin()`:```sqlcreate or replace function public.is_admin()returns booleanlanguage plpgsqlstablesecurity definerset search_path = publicas $$begin  return public.get_my_role() in ('admin', 'super_admin');end;$$;```Each RLS policy includes an `OR public.is_admin()` clause for SELECT, and separate admin UPDATE policies. This means:- A regular user only ever sees their own records.- An admin user (same JWT, different role in DB) sees all records.- The frontend role check cannot be bypassed — the DB enforces it.---## 8. AI Verification Engine Integration PointThe admin dashboard and/or an AI worker server submit verification results as follows:### Worker Architecture```AI Worker Server (Node.js / Python)├── Receives: evidence storage_path + trip_id + expected_plate├── Downloads: private file via service-role signed URL├── Calls: Computer vision API└── Writes result back to Supabase using service_role key:PATCH /rest/v1/verification_results?id=eq.{verificationId}Authorization: Bearer {SUPABASE_SERVICE_ROLE_KEY}{  "status": "pass",  "image_quality": "clear",  "vehicle_detected": true,  "detected_plate": "GJ01AB1234",  "plate_match": true,  "vehicle_type": "Truck",  "confidence": 0.97,  "decision": "PASS",  "explanation": "Plate matches, clear image, vehicle detected.",  "processor_version": "grainshield-cv-v1.2",  "processing_completed_at": "2025-10-20T10:15:00Z"}```### Idempotency- Each evidence upload creates exactly ONE `verification_results` record with `status=pending`.- The worker queries `WHERE status='pending'` and updates (never inserts) the result.- Duplicate processing attempts are prevented by checking `status` before starting.---## 9.
